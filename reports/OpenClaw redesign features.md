# OpenClaw 2.0 adds teams, not safety

Your understanding is only partly correct. The team claim is mostly true. The security claim is weak. The stability claim has no proof. OpenClaw 2.0 is stable version **2026.8.1**. The Foundation released it on about 30-31 August 2026 ([InfoQ](https://www.infoq.com/news/2026/09/openclaw-2-release/)). The headline feature is shared "multiplayer" sessions. Several people join one live session and hand off work ([VentureBeat](https://venturebeat.com/technology/openclaw-2-0-is-here-what-it-means-for-enterprises)). But the docs state that one Gateway is one trust domain. Shared sessions are not tenant isolation ([Teams doc](https://docs.openclaw.ai/start/teams)). On security, the safe defaults cover network exposure only. Sandboxing and exec approvals are off by default. VentureBeat says the release "is not secure by default and requires deliberate configuration." On stability, the team did a large reliability pass. But many users had upgrade failures. The team shipped atomic updates on 18 September to fix this ([Official blog](https://openclaw.ai/blog/shipping-openclaw-updates-that-dont-break)). No independent source shows that 2.0 is more stable. Scope note: this report covers the self-hosted agent by Peter Steinberger. It does not cover the earlier Clawdbot and Moltbot renames. The notes do not cover them.

## The release rebuilt setup, the web UI, memory and sessions

Hannes Rudolph, Community Manager, announced the release on 30 August. He called it "by far the largest update in the history of OpenClaw" ([Official blog](https://openclaw.ai/blog/openclaw-2-accidentally)). The team did not plan a 2.0. It planned simpler install and a new browser app. The cleanup then spread across most of the code, and the team named it 2.0 ([Decrypt](https://decrypt.co/377135/openclaw-2-0-is-here-whats-new)). The scale is large. The release notes list **16,977 pull requests and 987 contributors**. The blog and press say 933 contributors. The sources do not agree on this count ([Release notes](https://docs.openclaw.ai/releases/2026.8.1)). The release date also differs: 30 August, 31 August or 1 September, depending on the source.

The main features follow. Each one comes from the release notes or from press reports of them.

The architecture change is small. Sessions and transcripts move from plain files to SQLite. A local Secret Store holds credentials apart from the agent environment. The Gateway daemon stays. No source shows a language, runtime, config-format or API change. The official blog says it "does not describe architecture." The team says it built 2.0 by using its own multiplayer sessions ("build OpenClaw with OpenClaw"). This showed flaws in the single-user design ([Decrypt](https://decrypt.co/377135/openclaw-2-0-is-here-whats-new)).

Some changes break old setups. Sessions created after the SQLite migration do not appear after a downgrade unless you have a backup. The QMD retirement removes reranking, query expansion and cross-agent transcript search. The OpenProse plugin is removed. The `codex/*` model routes become `openai/*`. Run `openclaw doctor --fix` to handle these changes, and make a verified backup first ([dsebastien](https://www.dsebastien.net/2026-10-03-openclaw-2-0-easier-setup-shared-sessions-same-security-defaults/); [intelligentliving](https://www.intelligentliving.co/openclaw-2-0-release/)). The official blog and InfoQ list no breaking changes. A reader who uses only those sources will miss them.

## Teams: real collaboration inside one trust boundary

Your team claim is correct in intent. OpenClaw was a "one agent, one owner" design. The docs now say the same Gateway "can run as a shared team deployment instead of a personal assistant. Only the configuration differs" ([docs.openclaw.ai](https://docs.openclaw.ai)). The shipped team features are real and detailed.

Sessions now track an immutable creator, an assignable owner and a history of prompters. The UI shows presence and typing indicators. Owners and admins decide if a user can read, suggest, draft or participate. Git co-author trailers are available ([Teams doc](https://docs.openclaw.ai/start/teams)). Roles live in `gateway.roles`. The default role is `guest`. A role can set `sessions.others` (`view` or `write`), permitted `agents`, maximum `scopes`, and `sandbox: "required"`. You assign a role with the Gateway method `users.setRole`. If a required sandbox cannot start, execution fails. It does not fall back to the host ([VentureBeat](https://venturebeat.com/technology/openclaw-2-0-is-here-what-it-means-for-enterprises)). Other admin features are a team Secret Store, a provider budget view, per-person provider accounts, an audit log, and a "Publish PR" flow for guests. OpenClaw never merges the PR ([Teams doc](https://docs.openclaw.ai/start/teams)).

The limits are as important as the features. The Teams doc says: "Everyone who can message a tool-enabled agent shares that agent's delegated tool authority." It calls session ownership and presence "collaboration guardrails, not isolation." A guest with `sessions.others: "view"` can still read every shared session, including tool output. The security doc says: "OpenClaw is not a hostile multi-tenant security boundary." For users who do not trust each other, use one Gateway for each tenant ("cells"). Fleet tools for cells are experimental ([VentureBeat](https://venturebeat.com/technology/openclaw-2-0-is-here-what-it-means-for-enterprises)). The notes show no SSO, OIDC, SAML or SCIM in the core Gateway. Identity comes from Tailscale or a trusted proxy such as Cloudflare Access. Memory is separate per agent, not per person. No per-user quotas appear in the notes.

Independent reviewers agree with this view. The Rundown says the sessions suit small, trusted teams that share one security boundary ([The Rundown](https://www.therundown.ai/tools/openclaw-2-0)). eesel.ai says multiplayer still runs on a Gateway you host. It says there is no managed team product or admin console ([eesel.ai](https://www.eesel.ai/blog/openclaw-2-0-review)). eesel sells a rival product, so it has a bias. Some third-party guides say the tool has no per-user permissions. Those guides likely predate `gateway.roles` and understate it. Their claims partly conflict with the official docs.

The Foundation answers the multi-tenant gap with a separate product. OpenClaw Enterprise (OCE) came out on 29 September 2026. It is a free, self-hosted, open-source control plane. The Foundation offers it for internal pilots only. Version 1.0 is still to come ([RuntimeWire](https://runtimewire.com/article/openclaw-enterprise-free-agent-control-plane); [VentureBeat](https://venturebeat.com/orchestration/openclaw-launches-free-enterprise-control-plane-for-persistent-ai-agents-backed-by-openai-red-hat-and-nvidia)). The multi-tenancy and audit claims for OCE rest mainly on one outlet ([Crypto Briefing](https://cryptobriefing.com/openclaw-enterprise-ai-agent-control-plane/)). No official paid tier exists. Paid hosting comes only from third parties. No named customer case study exists. Adoption claims come from project insiders. Vincent Koc, chief architect, says the team runs 60-70 agents on 6-7 machines. These claims are not verified ([The Neuron](https://www.theneuron.ai/news/openclaw-2-multiplayer-ai-agents-vincent-koc/)).

## Security: safer exposure defaults, permissive execution defaults

The earlier versions had serious problems. Koi Security audited 2,857 ClawHub skills and flagged **341 as malicious** (the "ClawHavoc" campaign) ([CSO Online](https://csoonline.com/article/4129393/openclaw-integrates-virustotal-malware-scanning-as-security-firms-flag-enterprise-risks.html)). CVE-2026-25253 let a web page steal the Gateway auth token. It was patched in 2026.1.29, but the patch was incomplete ([SecurityWeek](https://www.securityweek.com/openclaw-security-issues-continue-as-secureclaw-open-source-tool-debuts/)). Censys counted 21,639 public instances on 31 January 2026 (same source). The source counts differ, and some are unverified.

The current defaults split into two groups. The first group is on by default and protects exposure. On regular host installs the Gateway binds to loopback. Most channels answer an unknown DM sender with a pairing code. Groups use allowlists and mention gating ([Docs: gateway security](https://docs.openclaw.ai/gateway/security)). The second group is off by default and covers execution. The docs say: "Sandboxing is off by default" ([Docs: sandboxing](https://docs.openclaw.ai/gateway/sandboxing)). Exec approvals default to `security: full` and `ask: off` on gateway and node hosts. `autoAllowSkills` is `false`. `tools.exec.strictInlineEval` is `false` ([Docs: exec approvals](https://docs.openclaw.ai/tools/exec-approvals)). Plaintext secrets still work. SecretRefs are opt-in for each credential ([Docs: secrets](https://docs.openclaw.ai/gateway/secrets)). Container images default to an exposed bind. Docker users do not get the loopback protection. Agents with message-tool access can send across channels and providers by default. The docs say the sandbox "is not a perfect security boundary."

This matches the trust model in SECURITY.md. OpenClaw is "local-first agent infrastructure for trusted operators." Plugins are part of the trusted computing base. The model and agent are "not a trusted principal" ([SECURITY.md](https://github.com/openclaw/openclaw/blob/main/SECURITY.md)). Prompt-injection-only reports are out of scope. Public internet exposure and multi-adversary shared Gateways are also out of scope. So the default posture is a trusted single operator. Teams can tighten it with roles, required sandboxes and bound approvals. But the operator must turn these on.

External checks are real but limited. The Foundation published a recap of a Trail of Bits engagement on 21 September. It lists 27 private advisories and 3 hardening PRs. Of 24 rated findings, there were 0 Critical, 2 High, 16 Medium and 6 Low. All actionable issues are fixed ([OpenClaw blog](https://openclaw.ai/blog/openclaw-trail-of-bits-engagement-recap)). This is the project's own recap. The Trail of Bits report was not found. The scope was core permissions and user data. The recurring themes were permissions lost between steps, and approvals not bound to the exact resource. These themes matter most for shared sessions. The GitHub advisory list shows 73 advisories. Two High items were published on 11 September, after 2.0: exec approvals that outlive their working directory, and a WhatsApp login tool that reaches non-owner turns ([GitHub advisories](https://github.com/openclaw/openclaw/security/advisories)). Aggregators list two more CVEs published on 26 September: CVE-2026-100568 (CVSS 8.3) and CVE-2026-100596 (CVSS 8.8, non-owner users could change MCP config) ([TheHackerWire](https://www.thehackerwire.com/vulnerability/CVE-2026-100596/)). The notes did not check these against NVD. There is no paid bug bounty ([SECURITY.md](https://github.com/openclaw/openclaw/blob/main/SECURITY.md)).

My verdict is this. "More secure by default" holds for network exposure and DM access. It does not hold for tool execution. Nobody outside the project has tested the 2.0 defaults. The notes found no post-2.0 penetration test and no exposure scan. The high CVE count after release does not prove the product is unsafe. It may show heavy review. But it also does not support "significantly more secure." One unverified blog says some defaults became looser in later releases, for example `tools.sessions.visibility` and `tools.swarm.enabled` ([Substack](https://youcanbuildthings.substack.com/p/how-to-stop-openclaw-updates-from)).

## Stability: a large reliability pass, then a rough upgrade

The release notes describe "a very large reliability pass." They say update paths check the existing install first. They add clearer recovery tools (Doctor), and say accepted messages survive managed restarts ([Release notes](https://docs.openclaw.ai/releases/2026.8.1)). But the upgrade itself failed for many users. InfoQ reports that some upgraded smoothly. Others had migration problems, broken Gateways, lost automations and model auth errors ([InfoQ](https://www.infoq.com/news/2026/09/openclaw-2-release/)). On 18 September the Foundation changed the update flow. The old Gateway keeps running while the new one is prepared. On failure the system rolls back to the last working config. Jason Sy said the goal is to "always leave you with a working claw to at least diagnose what issues happened with the update." He also said updating is not "completely fixed" ([Official blog](https://openclaw.ai/blog/shipping-openclaw-updates-that-dont-break)).

The independent evidence leans against your claim. Alex Finn, an experienced user, asked his agent to upgrade itself. The agent stopped responding. A fresh install lost about 8 months of memories and skills. He says about 70% of his past updates broke. This is one person's experience, not a measured rate. It reaches us through a third-party summary ([openclawdatabase.com](https://openclawdatabase.com/news/videos/2026-08-31-openclaw-2-upgrade-breakage-review/index.md)). The Rundown makes no strong reliability claim. It warns that fast releases can bring breaking changes ([The Rundown](https://www.therundown.ai/tools/openclaw-2-0)). The one positive quote comes from eesel, which has a bias and gives no data. The size of the release adds risk. About half of all pull requests ever merged went into it ([InfoQ](https://www.infoq.com/news/2026/09/openclaw-2-release/)). The release also had a mislabel: npm `2026.9.1-beta.1` is really `2026.8.1-beta.4`.

Later releases focus on fixes. The 2026.10.4 stable release is a stability patch with no new features. It fixes Gateway sleep and clock recovery and shutdown hangs ([GitHub releases](https://github.com/openclaw/openclaw/releases)). The notes show no LTS policy, no support window and no uptime data. One security source mentions a "2026.7.33 LTS" build, but the stability notes found no LTS policy. So the notes do not settle this. Treat "more stable" as a goal that the team is still working toward. Pin versions, back up before each update, and keep a rollback path.

## Conclusion

The new view is this. 2.0 changed OpenClaw from a personal tool into a tool that a small trusted team can share. It did not change the security model. The project still assumes trusted operators. The new controls (roles, required sandboxes, bound approvals, Secret Store) give teams the means to be safe. They do not make a default install safe. The Trail of Bits themes, and the CVEs on non-owner access, show that the permission model between co-users is the weakest part.

For a decision, use these rules. Use 2.0 for a small team that trusts each other and shares one Gateway. Turn on sandboxing, required-sandbox roles and approvals before you add guests. Use one Gateway for each trust group. Wait for OCE 1.0 if you need real multi-tenancy. Do not rely on "more stable" until independent users report clean upgrades. Open questions remain: the exact release date, the contributor count, the license (MIT or Apache 2.0, sources conflict), and the status of CVEs in the latest release. Check those at the primary sources.
