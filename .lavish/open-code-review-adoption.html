Use OpenCodeReview’s contracts — not its whole runtime

Alibaba’s OpenCodeReview has several excellent ideas for deterministic review coverage. The right move for scott-cc is to graft those ideas onto the existing Review Panel, not install a second autonomous reviewer beside it.

The decision

Keep one review engine. Add the deterministic substrate Review Panel is missing.

Recommended direction Build a native changed-file inventory, selection manifest, and coverage ledger inside plugins/review-panel.

Every selected file gets a stable identity. Every review stage carries the same manifest hashes. A run cannot report converged while any selected file is skipped, failed, or unaccounted for.

Do not add

  • Another LLM/provider configuration
  • OCR telemetry or session storage
  • MCP setup commands
  • Remote install scripts
  • Automatic GitHub posting
  • Default test exclusions

What changes in the architecture?

The current pipeline packages one shared diff, but it lacks a canonical per-file ledger. The proposal inserts deterministic identity and selection before CAST, then mechanically reconciles coverage before CONVERGE.

Deterministic code owns factsGit identity, changed paths, binary/secret safety, canonical JSON, hashes, and coverage totals.
LLMs keep judgmentCAST still chooses lenses from actual diff content; seats still identify and explain findings.
Convergence becomes provableA clean narrative is insufficient. Coverage must be complete and mechanically validated.

Three adoption options

One option is clearly better. Pretending they are equivalent would be fake neutrality.

Reject

Deploy ocr review directly

  • Gets OCR’s complete review loop and GitHub integration.
  • Duplicates Hermes/Review Panel providers, transcripts, and orchestration.
  • Adds telemetry, credential, supply-chain, and MCP trust boundaries.
  • Current upstream issue reports a silent green no-op on some non-empty diffs.
Fit: low · operational surface: high
Later pilot only

Wrap ocr delegate

  • Uses OCR for deterministic selection without OCR-side LLM calls.
  • Could benchmark local selection and rule routing.
  • Still adds a pinned binary dependency and upstream semantics.
  • Safe only on synthetic fixtures after checksum and telemetry controls.
Fit: medium · use as evidence, not infrastructure
Recommended

Borrow the patterns natively

  • Preserves the existing seven-stage Review Panel.
  • Adds exactly the missing deterministic contracts.
  • Keeps tests first-class and avoids extra data egress.
  • Lets Foundry fail closed on incomplete coverage.
Fit: high · smallest durable architecture

The proposed run contract

Three new artifacts turn “we reviewed it” from a claim into a checkable statement.

INVENTORYfreeze file identities
SELECTdecision + reason
CASTchoose lenses
SPAWNreview assigned IDs
MERGEdedupe findings
VALIDATEchallenge claims
RECONCILEprove coverage
input-manifest.json

Mode, resolved refs, path, status, source, old path, blob/content identity, stable entry ID, manifest hash.

selection-manifest.json

One decision per changed entry: reviewable or excluded, with a closed reason vocabulary and counts.

coverage.json

One terminal state per selected entry: reviewed, skipped, or failed. complete is true only when all are reviewed.

The crucial failure boundary A genuinely empty diff may converge with explicit zero counts. A non-empty diff that selects zero files must fail with zero_reviewable_nonempty_diff. Green no-op reviews are worse than red failures because they lie.

Risks that matter

The proposal is intentionally narrow, but Git and review provenance are unforgiving. These are the failure modes to design around.

1Prompt/schema drift

Every stage must validate artifacts before consuming them. Otherwise the schema is decorative paperwork.

2Git edge cases

Renames, staged-delete/untracked-recreation, symlinks, odd filenames, and binary detection need NUL-delimited parsing and fixtures.

3Sensitive artifact retention

Review packages contain source. Keep them ignored, mode 0600 where practical, exclude secret content, and decide retention before CI use.

4False confidence

Schema validity proves shape and coverage, not reasoning quality. Independent validation remains necessary.

5Stale worktrees

Files may change after inventory. Blob identities and hashes must be rechecked before packaging and final reconciliation.

6Upstream churn

Any OCR evaluation must pin an exact checksum. latest has no place in a required quality gate.
