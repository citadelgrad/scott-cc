Yes—but not declaratively

Hermes does not currently expose a “run this hook only while skill X is active” option on register_hook(). Enabled plugin callbacks are invoked for their registered events.

We can still scope behavior precisely.

The callback immediately returns None unless the current session has loaded the beads skill. Hermes exposes on_skill_lifecycle with action="loaded", skill_name, and session_id, so a companion plugin can arm policy for that session and stay inert everywhere else.

Important distinction: the hook technically fires, but it performs no Beads lookup and cannot block anything unless the session is armed. This is conditional behavior, not a native per-skill hook registration feature.

Planned Hermes skill vs. PAS + separate Codex processes

This is the actual architectural choice: should one persistent Hermes agent execute the Beads workflow itself, or should PAS split that workflow into explicit stages handled by separate Codex processes?

Planned Hermes Beads skill

One continuous coordinator, optionally many workers. The main Hermes session owns the Beads lifecycle and user conversation. It can perform a bead itself or dynamically delegate independent beads to isolated subagents while preserving the overall plan.

  • Best coordinator context and easiest mid-task collaboration
  • Can adapt decomposition when scope or evidence changes
  • Can add parallel implementation and fresh review on demand
  • Workers need explicit task packets because they do not inherit the parent conversation or loaded skill
  • The skill guides behavior; optional hooks could later enforce a few local invariants per armed session

PAS pipeline + separate Codex processes

Several isolated agents, one explicit graph. PAS assigns selection, implementation, quality, review, approval, and publication to separate stages. Each Codex process must reconstruct context from the repository, Beads, and artifacts left by earlier stages.

  • Better separation of duties and genuinely fresh review
  • Graph ordering, retries, quality nodes, and waits make the workflow repeatable
  • Context handoffs are explicit—and lossy if artifacts are weak
  • More latency, model calls, and orchestration cost
  • Best for long, repeatable, semi-autonomous execution

Concrete example—implement one ready epic child: with the Hermes skill, the coordinator can handle the child itself or give it to one isolated worker, then launch a different worker for review. The parent retains your corrections and owns the final Beads update. With attractor-6im.dot, the same roles are fixed in advance as pipeline nodes: selection, implementation, objective quality, fresh review, approval, and publication. The PAS version buys a repeatable predefined machine; the Hermes version buys a coordinator that decides when parallelism and separation are actually useful.

Recommendation

The planned Hermes skill should be the default Beads workflow because most of your work is interactive and benefits from continuous context. PAS is the heavier execution mode for epics where fresh processes, explicit stage gates, autonomous retries, or independent review are worth the extra cost. They are alternative operating modes, not two enforcement layers that need to police each other.

How the Hermes skill works with a multi-bead swarm

The skill becomes the coordinator protocol. It does not need every worker to mutate Beads, and loading it in the main session does not automatically load it into isolated subagents.

01
The main Hermes agent chooses only independent ready beads.

It runs bd ready/bd show, checks dependencies and write-set overlap, claims each selected bead, and creates an isolated worktree or equally strong workspace boundary for each implementation lane.

02
Each worker receives one complete execution packet.

The delegation includes the exact bead ID, acceptance criteria, absolute worktree, allowed write set, constraints, verification commands, and required return fields. Workers cannot see the parent conversation unless that information is passed explicitly.

03
Workers build; the parent remains the sole Beads writer.

Each worker may read its assigned issue, implement, and test, but reports evidence instead of claiming, closing, or reprioritizing work. This avoids racing lifecycle updates and keeps project state coherent.

04
The parent independently verifies every returned lane.

A subagent summary is a self-report, not proof. Hermes inspects each worktree and diff, reruns the relevant gates, checks cross-lane compatibility, and can dispatch a separate fresh reviewer before integration.

05
The parent reconciles results back into Beads.

It integrates in dependency order, records evidence, closes only verified beads, and leaves failed or blocked beads open with a durable checkpoint. One failed lane does not turn successful siblings into “done.”

Recommended ownership model

Parent owns Beads; workers own code lanes. That gives us one authoritative lifecycle writer, isolated implementation, selective parallelism, and clean integration responsibility.

If workers must own their beads

Each child must be given explicit Beads authority and load the skill independently. Any skill-scoped hook must arm separately for that child session. The parent cannot assume its loaded skill or session state propagated.

This is a dynamic pipeline, not a hidden PAS clone.

Hermes decides the swarm shape from the live task, can ask you questions, and can add or stop lanes. PAS declares the stages and transitions before execution. Hermes delegate_task workers are also bounded by the parent session—if the parent is interrupted they are cancelled—so PAS remains the better choice for a durable unattended workflow.

What happens during a scoped Beads task

01
The Beads skill loads because the task is about tracked project work.

That remains a normal skill-selection decision. Merely being inside a Beads repository does not arm enforcement.

02
on_skill_lifecycle records this session as armed.

State is keyed by opaque Hermes session_id and cleared on reset/finalization.

03
Read-only exploration is still allowed.

The hook returns immediately for read_file, searches, web research, and other non-mutating operations.

04
The agent uses native bd commands.

No replacement verbs. A successful bd update <id> --claim establishes the session’s issue binding.

05
Only then do mutation and finish gates apply.

If the session is unarmed, every callback returns None. If armed but unclaimed, durable mutation can be blocked.

What a skill cannot do

A skill is guidance

It can tell the agent to claim before editing and update before finishing. It cannot intercept patch, terminal execution, or the final-response transition.

A hook is enforcement

If we truly need “this operation must not happen,” some executable integration is required: a plugin hook or shell hook. A markdown skill cannot provide that guarantee.

Honest limitation: current Hermes hooks have no declarative skill matcher. The implementation must maintain the armed-session set itself. We would test preload, normal skill_view, resume, reset, compression, subagents, and parallel sessions before trusting it.

Recommendation

Do the skill work first. Don’t build the plugin yet.

  1. Update the existing beads skill with the concrete workflow improvements from the session review.
  2. Use it across real Beads tasks and record actual misses: unclaimed mutations, absent checkpoints, premature completion, ambiguous parallel ownership.
  3. Only if those misses persist, build a tiny optional hook companion scoped by on_skill_lifecycle.
  4. Keep the companion unnamed in normal use—it exposes no tool, CLI, or slash command. Its package name is implementation detail.

This preserves the useful idea—hooks can enforce boundaries—without prematurely turning a workflow problem into permanent runtime machinery.

Grounding

  • Hermes on_skill_lifecycle exposes action, skill_name, task_id, and session_id.
  • Hermes pre_tool_call can block, approve, or modify tool calls and fails closed on timeout.
  • Hermes plugins can bundle skills and register hooks, but skills themselves do not register executable lifecycle callbacks.
