01 / Working recommendation

Explore classification. Do not replace reasoning.

Investigate NixonNote and Field Guide first.

Fixed-taxonomy note organization and bounded query classification look like safer starting points than autonomous decisions. Both can be evaluated offline and kept advisory while the existing behavior remains intact.

This is a prioritization hypothesis, not an adoption recommendation. The winning candidate depends on representative labels, an actual decision bottleneck, and an advantage over the simplest baseline.

Most direct comparison

Jev compaction

Your existing plugin already uses a typed-decision service. But it allows a 25,000-token state and a 30,000-token request, while Laya’s advertised checkpoints use much shorter contexts. That is a semantic mismatch, not an adapter detail.

Do not attempt a drop-in replacement. Investigate whether a bounded per-item decision preserves enough dependency evidence first.

Hard boundary

No autonomous authority

Laya must not authorize tool execution, declare security clearance, pass a failed quality gate, issue a refund, delete session history, or complete a goal.

Typed output makes a decision easy to consume. It does not make the decision correct.

02 / Technical model

A classifier inside a guarded workflow

Laya exposes three decision primitives: choice for a fixed set of categories, score for an ordinal rubric, and noul for a boolean probability. It does not generate explanations, summarize notes, or invent a new taxonomy. [1]

1. Bound the inputKeep relevant evidence. Reject or abstain if it cannot fit.
2. Ask a typed questionUse a fixed rubric and a deliberately selected checkpoint.
3. Validate & abstainCheck structure, limits and a domain-tested threshold.
4. Suggest, don’t actHuman review or existing behavior remains the fallback.

04 / New-product hypotheses

Prefer a useful feature to another platform.

No demand research has been completed for these concepts. Each needs a concrete user, recurring volume and lawful labels before it deserves implementation.

A / PRIVATE INTAKE

Multilingual review inbox

Incoming support messages become suggested queues with a visible correction step. Keep message bodies off hosted classification services where feasible.

Reject if: an existing helpdesk solves the problem or language-specific error rates are unacceptable.

Likely home: a feature in an existing support workflow, not a new company.

B / WORKFLOW REVIEW

Local failure-review queue

Short failure events are grouped into review categories. Original logs and deterministic status remain visible.

Reject if: signatures and exit codes give the same benefit without model maintenance.

Likely home: Foundry or another existing operations interface.

C / DOCUMENT INTAKE

Private document sorter

Short documents or bounded excerpts enter a fixed taxonomy with manual confirmation and traceable source text.

Reject if: whole-document reasoning is needed, or chunking loses decisive evidence.

Likely home: NixonNote if the workflow overlaps personal knowledge capture.

06 / First experiment proposal

One offline candidate. No production integration.

Proposed—not executed

Start with NixonNote fixed-taxonomy classification only if representative notes can be used locally with approval. If labels or taxonomy are unavailable, assess Field Guide’s query-classification data instead. Do not build both experiments by default.

Data contract

  • Define labels and a human correction rubric before collecting predictions.
  • Keep private notes local; do not upload them to teachers, demos or public tools.
  • Split by original document/thread before chunking; keep near-duplicates and translations together.
  • Separate training, calibration and untouched test sets.
  • Size the dataset for the chosen error tolerance. Synthetic examples verify mechanics, not real-world quality.

Evaluation contract

  • Compare majority baseline, simple classifier, current behavior and Laya on the same examples.
  • Report per-class precision/recall, macro-F1, confusion matrices and calibration.
  • Pick abstention thresholds on calibration data only; freeze before final testing.
  • Measure correction burden and coverage—not only top-label agreement.
  • Treat base and fine-tuned models as separate experimental arms.

Operational checks

  • Pin package, dependency lock, model, tokenizer and encoder revisions.
  • Record actual device, input length, rubric length, batch size, memory and cold/warm timing.
  • Exercise empty, oversized, multilingual and code-switched inputs.
  • Exercise load failure, timeout, invalid outputs and accelerator fallback.
  • Keep original content and existing behavior intact on uncertainty or failure.

Decision gate

  • Choose quality and critical-error tolerances before running the held-out test.
  • Require a concrete advantage over the simple baseline and current behavior.
  • Reject if context reduction removes necessary evidence.
  • Defer if lawful labels, reproducible weights or runtime budget are missing.
  • Adoption requires a separate exact-file implementation and TDD plan.
07 / Remaining investigation

What must happen before a final recommendation

  1. Reproducibility audit: freeze upstream and Hub revisions, inspect licenses and loading paths, resolve the benchmark-notebook/version mismatch noted in reconnaissance.
  2. Evidence audit: trace benchmarks to splits, teachers, calibration data and timing boundaries; look for independent reproductions.
  3. Portfolio audit: follow real functions, callers and tests for each finalist. Resolve Field Guide source access and Rosco checkout ownership.
  4. Data audit: establish actual taxonomy, volume, label availability, privacy conditions and failure consequences.
  5. Alternative comparison: compare the existing path, a simple baseline and Laya; verify current prices only where costs matter.
  6. Experiment specification: select one candidate, exact input contract, budget and predeclared gates—or write a no-go.
  7. Adversarial review: challenge provenance, context fit, leakage, downstream harm and unnecessary complexity before publishing the final decision.
